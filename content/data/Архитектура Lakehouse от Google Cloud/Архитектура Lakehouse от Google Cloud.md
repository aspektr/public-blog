Сегодня организациям требуется надежная и масштабируемая основа данных для поддержки их растущих потребностей. Архитектура Lakehouse предлагает современный подход, сочетая масштабируемость и гибкость хранилища данных с транзакционными возможностями, производительностью и безопасностью хранилища данных.

Этот подход позволяет бизнес-пользователям получать доступ к данным с необходимой скоростью и надежностью, не полагаясь на различные инструменты и технологии. Он решает распространенные проблемы, такие как изолированные данные, непоследовательное качество данных и медленный доступ к информации.

Кроме того, архитектура Lakehouse предоставляет технические возможности для хранения, обработки и доступа к данным в масштабе, независимо от их структуры или формата. Это поддерживает самостоятельный доступ к данным и обмен данными — ключевые аспекты современной стратегии работы с данными. Используя один слой хранения для всех данных, организации могут использовать различные движки обработки данных в зависимости от конкретного случая.

Модель работы Data Mesh является идеальным дополнением к этой архитектуре, раскрывая ее полный потенциал. Принципы Data Mesh облегчают управление, доступ и управление данными в различных доменах внутри организации. Это обеспечивает надлежащее обращение с данными как с ценным активом, способствует сотрудничеству и снижает изоляцию данных.

Data Mesh — это архитектурная и организационная структура, которая рассматривает данные как продукт. Команды, которые лучше всего понимают свои данные и следуют общим стандартам управления данными в организации, наиболее эффективно разрабатывают данные продукты. После развертывания продуктов распределенные команды могут быстрее и эффективнее обнаружить и получить доступ к данным, которые имеют отношение к их нуждам.

Для того чтобы Data Mesh функционировал эффективно, необходимо сначала установить высокоуровневые архитектурные компоненты и организационные роли.

Основные принципы Data Mesh:

- **Децентрализованное владение данными и архитектура, ориентированная на домены**: данные организуются, а владение данными распределяется по доменам, с децентрализованным владением данными в рамках бизнес-специфических доменов данных, которые централизованно управляются и контролируются. Такая организационная структура создает экосистему, производящую и потребляющую данные, которая может масштабироваться с увеличением числа источников данных, числа вариантов использования и разнообразия моделей доступа к данным.
    
- **Данные как продукт**: логическое объединение данных, которое позволяет пользователям данных легко находить, понимать и безопасно использовать данные высокого качества. Продукты  могут быть классифицированы как ориентированные на источник, агрегированные или ориентированные на потребителя, и шаблонизированы для записи намерений каждого продукта данных в согласованной форме. Затем продукты данных могут быть обнаружены, получены, использованы, управляемы и контролируемы в соответствии с установленными SLA.
    
- **Самостоятельная инфраструктура данных как платформа**: позволяет командам по доменам создавать и потреблять продукты данных автономно с использованием абстракций Google Cloud Platform, скрывая сложность построения, выполнения и поддержания безопасных и совместимых продуктов данных.
    
- **Федеративное вычислительное управление**: стандартный набор инструментов и утилит для команд по доменам, а также стандартизированные элементы и форматы метаданных, которые команды продуктов будут использовать при создании и управлении каждым продуктом данных.

**Автоматизация и самообслуживание** Чтобы быть действительно эффективной, ранее описанная реализация на Google Cloud должна быть максимально автоматизированной и обеспечивать самообслуживание для команд, занимающихся платформой данных, управлением данными, производителями данных и потребителями данных.

При этом подходе:

- Команда по управлению данными может самостоятельно обслуживать свои потребности в отчетности, исследуя журналы доступа, соблюдение контрольных правил, отслеживание происхождения данных, информацию по управлению и другие аспекты, управляя своими данными.
    
- Команда по платформам данных может описать все необходимые инфраструктурные блоки в шаблонах Terraform (Infrastructure-as-Code), с CI/CD пайплайнами для развертывания и настройки всех сервисов Google Cloud, необходимых для создания продукта данных в соответствии с установленными правилами.
    
- Команда производителей данных может использовать эти компоненты как фабрику для быстрого и последовательного создания повторяемых продуктов данных, зная, что все элементы безопасности, мониторинга, интеграции с управлением и другие аспекты уже встроены в продукт данных. Команда потребителей данных может быстро и легко находить, запрашивать доступ и начинать использовать продукты данных без необходимости взаимодействовать с командой производителей данных, за исключением, возможно, процесса утверждения доступа.
    

Цель этого подхода — снизить количество коммуникаций и передач артефактов между командами, уменьшив тем самым неявные задержки, которые такие действия могут вызвать, при этом все равно предоставляя командам необходимую информацию в рамках надежного управления.

### Общие фреймворки — Управление данными

Управление данными является ключевым элементом успешного проекта. Это широкий термин, касающийся безопасности и управления чувствительными данными, а также того, как обеспечить понимание конечными пользователями того, какие данные доступны в бизнесе, и как они могут запросить доступ к ним. Для управления данными Dataplex является унифицированным слоем управления на платформе данных Google Cloud.

Правильная модель управления данными часто требует:

- Содействия сотрудничеству между командами IT, данными и бизнесом
    
- Создания фреймворка, который позволяет каждому заинтересованному лицу решать свои задачи с высоким уровнем автономии, при этом следуя лучшим практикам, определенным IT-отделом
    
- Обеспечения самостоятельной аналитики и быстрого времени до получения информации
    
- Внедрения лучших практик в области безопасности, DevOps/DataOps, соблюдения нормативных требований и стандартов
    
- Обеспечения быстрого построения и доставки моделей уровня производства для команд по данным
    

Однако настройка правильной модели управления данными на масштабируемом уровне — это не простая задача. Традиционные подходы, которые полагаются на центральную команду данных для обработки большинства этапов жизненного цикла данных, от сбора данных и их трансформации до обеспечения качества и безопасности данных, а также до определения бизнес-метрик (KPI), не смогли масштабироваться и обеспечить ожидаемые результаты в большинстве организаций, как показано на иллюстрации ниже:

Он объединяет потоковую загрузку и пакетную загрузку в одно высокопроизводительное API. API записи данных можно использовать для потоковой передачи записей в BigQuery в реальном времени или для пакетной обработки произвольного количества записей и их фиксации в одной атомарной операции. Этот API записи интегрирован с Datastream для применения изменений в таблицах BigQuery в автоматическом режиме с использованием CICD.

Существует множество вариантов для проектирования шаблонов загрузки данных, включая Datastream, Pub/Sub и другие, и правильный подход можно выбрать только на основе конкретных случаев использования и нефункциональных требований организаций.

[Analytics Hub](https://cloud.google.com/analytics-hub) - это безопасная платформа обмена данными от Google, которая позволяет организациям создавать библиотеку внутренних и внешних данных с поддержкой BigQuery.

С помощью Analytics Hub организации могут выступать как подписчиками данных, так и их издателями, как для внутренних, так и для внешних данных.

Analytics Hub делит данные на три классификации: **Публичные**, **Частные** и **Организационные**.

Как подписчик внешних данных, будь то публичные или частные, организации могут потреблять внешние наборы данных, такие как данные ESG от Morningstar. Google расширяет количество курируемых наборов данных и активно сотрудничает с организациями в этой области, чтобы обеспечить большую доступность поставщиков данных.

**Организационные данные** позволяют организациям делиться большими наборами данных внутри компании без необходимости их перемещения. Например, организации могут объединять несколько наборов данных в один и публиковать его внутри организации для внутреннего потребления.

Как издатели, организации могут публиковать контактные данные менеджера продукта данных, категорию данных и другую документацию, чтобы помочь потребителям правильно использовать эти данные — эта информация затем становится доступной для потенциальных пользователей. Также можно ограничить выход данных, чтобы предотвратить копирование и экспорт общих данных и/или результатов запросов.

Обмен данными часто вызывает вопросы по поводу суверенитета данных и законодательства, такого как GDPR. Чтобы соответствовать этим требованиям, может быть создан обмен данными в Analytics Hub для конкретного региона, и он может содержать объекты BigQuery, доступные только в этом регионе.

Для общих наборов данных поддерживается безопасность на уровне строк и столбцов.

**Обнаружение наборов данных**  

Как и с API-продуктами, наборы данных в Analytics Hub должны быть сначала обнаружены, прежде чем они могут быть использованы. Это возможно через Google Cloud Console и API. При поиске наборов данных можно применить фильтры для нахождения соответствующей категории, классификации данных или поставщика.

Потенциальные потребители могут ознакомиться с документацией набора данных, предоставленной издателем, и решить, подходит ли данный набор данных для их нужд.


**Отчеты по наборам данных**  

Метрики использования в Analytics Hub позволяют издателям визуализировать агрегированные данные об использовании, задачах, выполняемых с общим набором данных, и другую информацию о потреблении. Отправка этих данных в Looker может упростить визуализацию всех данных, связанных с данным продуктом, в одном окне. 

**Семантический слой Looker**  
Looker — это корпоративная платформа Google Cloud для бизнес-анализа, приложений для данных и встроенной аналитики. Семантический слой моделирования Looker позволяет компаниям стандартизировать бизнес-логику по всей организации.

В контексте организации data mesh и data product, Looker ML играет важную роль, так как он абстрагирует физическое местоположение данных в различных продуктах данных и предоставляет полный обзор данных, управляемых в разных продуктах для BI. Семантический слой, построенный в LookerML, можно использовать для создания визуализаций в Looker, Tableau, Power BI и других BI-инструментах.
