Ниже представлен структурированный 90-дневный план для ведущего системного аналитика, охватывающий ключевые цели на каждый месяц.

🎯 **Месяц 1: Ознакомление, погружение, низко висящие плоды**  
📌 Цели:  
✅ 1. Понять бизнес и архитектуру системы

- Изучить существующие бизнес-процессы, архитектуру системы и ключевые интеграции.
- Выявить узкие места, зависимости и болевые точки.
- Провести встречи с заинтересованными сторонами (продукт, разработка, QA, devops, frontend), чтобы понять требования.

✅ 2. Оценить документацию и текущие рабочие процессы

- Изучить существующую системную документацию, требования и технические спецификации.
- Выявить пробелы в документации и предложить улучшения.
- Оценить используемые инструменты для документации (JIRA, Confluence).

✅ 3. Оценить и улучшить процессы системного анализа

- Выявить неэффективности в сборе и анализе требований.
- Предложить быстрые улучшения процессов (например, улучшение шаблонов, лучшая работа с бэклогом).

✅ 4. Установить четкие каналы коммуникации

- Определить стандартный формат для спецификаций требований ([[BRD vs FSD| BRD - Business Requirements Document, FSD - Functional Specification]] Document, user stories, use cases и т. д.).
- Выровняться с командами разработки и инфраструктуры по формату документации.
- Организовать еженедельные синхронизации с различными ролями в команде.

✅ 5. Первые быстрые победы

- Проревьюить хотя бы один важный документ требований и улучшить его четкость.
- Дать обратную связь по текущей архитектуре системы с предложениями по улучшению.
- Убедиться, что все бизнес-правила хотя бы одного важного компонента системы задокументированы.

🎯 **Месяц 2: Оптимизация и улучшение процессов**  
📌 Цели:  
✅ 1. Улучшить управление требованиями и прослеживаемость

- Стандартизировать процессы сбора и утверждения требований.
- Внедрить [[Матрица прослеживаемости требований - RTM| матрицу прослеживаемости требований (RTM)]] для отслеживания изменений.
- Обеспечить версионность всех системных требований.

✅ 2. Улучшить взаимодействие между бизнесом и разработкой

- Ввести структурированные совещания для обзора требований.
- Провести обучение для команд по написанию четких, недвусмысленных требований.
- Обеспечить согласование требований между командами Dev, QA и PM.

✅ 3. Оценить масштабируемость системы и риски

- Выявить потенциальные узкие места в архитектуре системы.
- Провести анализ влияния предстоящих релизов фич.
- Определить процесс ранней оценки рисков для изменений в системе.

✅ 4. Определить KPI и отчетность по системному анализу

- Установить метрики для отслеживания качества требований системы (например, процент дефектов из-за неясных требований).
- Создать ежемесячную отчетность по точности и полноте требований.

✅ 5. Обеспечить ключевые улучшения процессов

- Разработать/уточнить диаграммы use case, движения данных и моделей данных в проекте.
- Работать с Dev/QA для улучшения покрытия тестами на основе улучшенных требований.
- Обеспечить использование единого рабочего процесса системного анализа во всей команде.

🎯 **Месяц 3: Стратегические инициативы, долгосрочные улучшения и масштабирование**  
📌 Цели:  
✅ 1. Внедрить стратегию долгосрочного системного анализа

- Определить лучшие практики для системных аналитиков в проекте.
- Внедрить процесс обмена знаниями между аналитиками.
- Нанять/обучить младших аналитиков критически важным принципам проектирования систем.

✅ 2. Оптимизировать документацию и инструменты

- Внедрить инструменты для автоматической генерации документации (например, PlantUML, Mermaid.js).
- Улучшить документацию API и спецификации системных интеграций.

✅ 3. Усилить межкомандное сотрудничество

- Провести совместные планирования с разработчиками и менеджерами.


✅ 4. Пересмотреть и улучшить управление изменениями

- Установить процесс эффективного управления изменениями в требованиях.
- Обеспечить проведение оценки влияния перед крупными обновлениями системы.

✅ 5. Оказать ключевое влияние на бизнес

- Выявить одно ключевое бизнес-требование, которое было улучшено благодаря лучшему анализу.
- Снизить хотя бы один важный риск, связанный с плохой документацией системы.
